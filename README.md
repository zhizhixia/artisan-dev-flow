# 🧭 Enough —— 够用就好（enough）

> 模型已经足够强大，轮子已经足够丰富，缺的只是一个恰到好处的引导。

[English](README.en.md) | [中文](README.md)

Enough 是一个给 AI 编程助手（Codex、Claude Code、OpenCode 等）用的 Skill——你可以把它理解成一份可执行的开发流程说明。装上之后，AI 帮你开发软件时会按一套经过验证的流程走，而不是想到哪写到哪。它轻到 10 秒装完，小到只有 300 余行，新手也能零配置直接用。

## 为什么要做这个东西？

如果你经常让 AI 帮你写功能，大概率遇到过下面这些情况：

**1. 白干一场**
AI 兴致勃勃写了一堆代码，你后来才发现 GitHub 上早就有一个现成项目，功能几乎一模一样。改别人的代码比自己从零写省一半时间。

**2. 方向错了才发现**
AI 没问清楚你要什么就开始动手，或者一次抛给你五个问题让你自己选。做到一半你才意识到方向不对，返工。

**3. 什么都做，什么都不通**
AI 同时铺开十个模块，看起来进展飞快。最后集成的时候发现：主流程根本跑不通，所有模块都是空中楼阁。

**4. "构建成功"不等于"能用"**
AI 说"测试全过了"，其实只是代码能编译、单测是假的，你实际点开程序一用就崩。

**5. 发布事故**
密钥写进了代码、临时文件混进了仓库、调试配置没关——上线后才发现。

**6. 同一个问题修不好**
AI 反复"猜"同一个 bug，改一次崩一次，从来不停下来查根因。

Enough 就是为了解决这些问题而生的。它把"靠谱工程师"的工作习惯写成了 AI 能照做的流程。

## 核心理念

模型的能力已经足够，网上的轮子已经足够。Enough 的信念很简单：开发这件事，缺的从来不是更多能力，而是在关键节点上恰到好处的引导。

现在的大模型已经足够强悍：强悍到能独立写出一整座代码库，也强悍到"顺手"就把轮子重新造了一遍；它足够自信，自信到把密钥直接写进代码、把 `.env` 一路提交到 GitHub。

它缺少的从来不是能力，而是在关键节点上的"把关"——动手前是否完成开源方案评估，编码前设计规格是否通过评审，全面开发前最小可用闭环是否跑通，宣布完成前验收证据是否充分，发布前敏感信息和临时产物是否已经清理。

Enough 就是这个把关者。它不教 AI 怎么写代码——这不需要教；它只在最容易翻车的关键节点，让 AI 停下来想一秒：先复用，先批准，先验证，先检查。

| 关键节点 | 把关问题 | 对应门禁 |
| --- | --- | --- |
| 动手前 | 是否完成开源方案评估？ | 复用决策 |
| 编码前 | 设计规格是否通过评审？ | 设计批准 |
| 全面开发前 | 最小可用闭环是否跑通？ | 纵向闭环 |
| 完成声明前 | 验收证据是否充分？ | 验收证据 |
| 发布前 | 敏感信息与临时产物是否清理？ | 发布检查 |

## 它到底是什么？

市面上已经有很多 AI 开发方法论（Superpowers、Spec Kit、Trellis 等），做得又大又全。Enough 不一样：

- **它是个"编排器"**，不是新造一套轮子。它只负责流程顺序、决策门禁和质量底线，具体干活还是交给现有的能力。
- **它非常轻**：整个 Skill 只有 4 个文件、300 余行。拷贝即用，不安装任何依赖，不改变你的工具链，10 秒完成安装。
- **它对新手友好**：零配置，不需要你懂任何框架。它会用大白话解释每一步在做什么、为什么，你只需要回答它提出的一两个选择题。
- **它工具无关**：你的环境里有没有 Trellis、有没有 CodeGraph，它都能用——缺了就用简化版顶上。

名字的来历：Enough——不是"够用就好"的将就，而是"已经够了，不必再折腾"的清醒：模型的能力已经足够，开源的积累已经足够，真正缺的从来不是更多能力，而是在关键节点上轻轻点拨的那一下。

## 它是怎么工作的？

### 第一步：分清活儿的大小

不是所有任务都要走完整流程。Enough 把任务分成三档：

| 档位 | 什么任务 | 怎么处理 |
| --- | --- | --- |
| 🐇 快速路径 | 改错字、小修小补 | 直接做，不搞仪式 |
| 🏗️ 标准路径 | 新项目、新功能、跨模块修改 | 走完整流程 |
| 🚨 高风险路径 | 涉及钱、账号、隐私、外部写操作、部署、工业设备 | 完整流程 + 额外保险（试运行、回滚、小范围先验证） |

### 第二步：八步流程

1. **开源方案评估**（GitHub 复用门禁）——先检索开源生态，评估是否有可直接采用或扩展的成熟实现，而不是从零开始。发现高度匹配的项目时，建议直接采用；平台、数据边界等关键约束变化后会重新评估结论。
2. **现状分析**（代码考古）——分析现有代码的结构、数据流和既有工程约定。必要时建议建立代码索引（CodeGraph），但须经你同意。
3. **设计评审**（设计批准）——明确目标、非目标、验收标准和模块边界，形成设计规格。只逐项询问真正改变方向的问题，其余采用有理由的推荐默认值。**设计未通过评审，禁止编码。**
4. **验证计划**——编码前先定义"如何证明可用"：静态检查、自动化测试、真实运行验证的分层与证据要求。
5. **最小纵向闭环**——先打通一条贯穿真实系统的最小完整路径（例如：启动 → 用户操作 → 数据持久化 → 结果呈现）。**闭环未通过，禁止全面铺开。**
6. **受控实现**——默认串行完成核心契约与集成路径；长任务拆成可独立验收的里程碑，仅对相互独立的任务并行，通常最多 2–3 条工作线。状态只在完成、阻塞或下一步实质变化时更新。
7. **验收与排错**——先验证主流程，再验证边界与失败路径；重要写入须重新读取或检查差异，验收须逐项对照批准的标准并附证据。同一路径连续失败两次，先区分代码、环境、权限或工具问题。
8. **发布与沉淀**——发布前检查敏感信息与临时产物，明确已验证/未验证范围与回滚方案；仅沉淀值得复用的经验。

### 五道门禁

流程里还有五个"不过不许进下一道工序"的检查点：

1. 没有复用决策 → 不许开始自建。
2. 没有设计批准 → 不许写代码。
3. 最小纵向闭环没过 → 不许扩大并行。
4. 没有逐项验收对账和证据 → 不许说"完成"。
5. 没有安全和发布检查 → 不许对外发布。

### 它还会守住的底线

- 密钥只从环境变量读取，绝不写进代码、日志或聊天记录。
- 用户说"只读、别动文件"，就真的一个文件都不创建。
- 没经用户同意，不提交、不推送、不发布。

## 解决了什么问题？（对照表）

| 你遇到的痛点 | Enough 怎么解决 | 对应机制 |
| --- | --- | --- |
| 白干一场 | 动手前强制搜索 GitHub，找到现成项目就建议直接用 | 第 1 步 + 门禁 1 |
| 方向错了才发现 | 设计评审通过后再动工，一次只问一个关键问题 | 第 3 步 + 门禁 2 |
| 什么都做、什么都不通 | 先打通最小纵向闭环，再受控并行 | 第 5、6 步 + 门禁 3 |
| 假测试、假完成 | 逐项对照验收标准，核验写入落盘，区分 Mock 和真实验证 | 第 4、7 步 + 门禁 4 |
| 发布事故 | 发布前安全检查，密钥/临时文件/调试配置清点 | 第 8 步 + 门禁 5 |
| 同一个 bug 修不好 | 连续两次失败就转根因分析，禁止瞎猜 | 第 7 步 |
| AI 过度自信 | 完成报告必须区分"已验证 / 部分验证 / 未验证" | 第 8 步 |

## 真实案例：它帮使用者避开了什么

**案例：想做一个 RSS 阅读器，结果一行代码都没写。**
一位使用者提出需求："Windows 本地 RSS 阅读器，多源订阅、关键词过滤、定时刷新、一键安装。"Enough 没有立刻开始写代码，而是先搜索 GitHub——发现 RSS Guard 四项功能全部原生满足、维护活跃、提供官方安装包，于是直接建议采用。结果是：零行代码，需求当天满足。这正是"复用优先"要的效果。

另一个完整案例中，用户从“进阶日记”逐步确定为原生 Android、本地存储和系统身份认证，Enough 因关键约束变化把复用结论从“扩展现成项目”调整为“只借鉴数据模型、原生自建”，再按纵向闭环和里程碑完成设备验收。案例也如实保留了迁移测试与文档写入缺口，见 [Mind Journal 端到端案例](examples/mind-journal-end-to-end.md)。

更多输入→输出示例见 [examples/](examples/)。

## 快速开始

**一键安装（推荐，GitHub 官方 CLI）**：

```bash
gh skill install zhizhixia/enough enough --agent codex --scope user
```

`--agent` 支持 40+ 客户端（claude-code、opencode、cursor、gemini-cli 等），`--scope user` 表示全局生效。也支持从本仓库安装后自动更新：`gh skill update enough`。

**手动安装（零依赖）**：把 `skills/enough/` 文件夹拷贝到对应客户端的 skills 目录，例如 Codex 是 `~/.codex/skills/enough/`（包含 `SKILL.md`、`references/` 和 `agents/`），重启客户端即可自动发现。

**使用**：直接说"按我的开发流程推进 XXX"，或者自然描述一个新项目、新功能、高风险修复任务，Enough 会自动触发。

**可选依赖**：brainstorming、verification-planning、Trellis、CodeGraph 等。装齐体验最好；没装也完全能用，Enough 会自动降级为简化版流程。

## 适合谁？

- 用 AI 辅助写代码，但希望 AI "靠谱一点"的开发者。
- 一个人同时维护多个项目、不想重复造轮子的人。
- 项目涉及真实设备、真实账号、真实数据，容不得"差不多就行"的人。
- 刚接触 AI 编程、想从一开始就养成好习惯的新手。

## 和其他方法论相比

市面上已有的 AI 开发方法论解决不同层次的问题。Enough 的定位是"极轻的流程引导"：

| 维度 | **Enough** | Superpowers | OpenSpec / Spec Kit |
| --- | --- | --- | --- |
| 安装 | 拷贝文件夹，10 秒 | 安装插件 + 技能库，按工具逐一适配 | 安装 npm CLI + 初始化规格目录 |
| 体积 | 4 个文件、300 余行 | 数十个 Skill 与脚本 | CLI 工具 + 规格目录结构 |
| 依赖 | 零依赖、零配置 | 依赖对应工具的插件机制 | 需要 Node 20+，命令由 CLI 驱动 |
| 定位 | 流程编排与门禁 | 完整方法论 + 技能体系 | 规格驱动的开发框架 |
| 可迁移性 | 纯 Markdown，任何 AI 工具可读 | 每个工具单独适配 | 绑定 CLI 环境 |
| 复用优先 | 第一回合硬门禁，强制评估开源方案 | 无强制 | 无强制 |
| 轻任务处理 | 有快速路径，小事不搞仪式 | 有轻量路径 | 仍走完整规格流程 |
| 能力缺失时 | 自动降级为简化流程 | 依赖技能套件完整性 | 不适用，CLI 是硬依赖 |

**什么时候选 Enough**：个人或小团队、多工具环境（Codex / Claude Code / OpenCode 混用）、想用最少的仪式获得关键门禁、尤其看重"动手前先找现成轮子"。

**什么时候选它们**：需要团队级规格管理与跨仓库协作，选 OpenSpec / Spec Kit；想要一套开箱即用的完整方法论全家桶，选 Superpowers。它们和 Enough 不冲突——Enough 可以站在它们之上，只补流程编排与决策门禁。
