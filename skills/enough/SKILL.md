# Enough 开发流程

## 核心原则

<CRITICAL>
对标准路径和高风险路径，首个开发回合必须以用户可见的“复用决策”结束。发送最终答复前检查：候选、证据等级、明确推荐、理由、搜索限制和下一步是否都已给出。内部状态句、研究进度或“稍后输出”不是合法结果；即使搜索失败或超时，也要输出部分复用决策并说明限制。
</CRITICAL>

默认使用中文沟通；若用户使用其他语言，跟随用户语言。优先复用、长期维护和可验证结果。一次只确认一个真正影响范围、架构、成本、安全或外部状态的问题，并同时给出推荐与理由。普通且可验证的技术选择自行推进，说明假设即可。

严格遵守用户给出的写入范围。用户要求只读、不要修改文件或只做规划时，不创建分析笔记、克隆、临时文件、索引或其他磁盘产物；把分析保留在对话中。

把自己当作集成负责人。复用现有 Skills，不复制其完整流程；能力不可用时执行等价的简化步骤。

## 前置条件与自动降级

本流程是编排器，不依赖任何特定工具。可选的配套能力包括：brainstorming（需求设计）、verification-planning（验证设计）、Trellis Implement/Check（实施与检查）、break-loop（连续失败排错）、simplify（维护性优化）、reflect（经验沉淀）、CodeGraph（代码索引）。

这些能力缺失时，按正文中的降级规则执行等价的简化步骤，不要中断任务。

## 选择路径

先判断任务深度并简短说明选择：

- **快速路径**：文档、格式或明确局部的低风险修改。保护工作区并运行相称检查；除非引入新行为或用户明确要求，否则跳过 GitHub 搜索和正式设计文档。
- **标准路径**：新项目、非简单功能、跨模块或跨系统修改。执行完整流程。
- **高风险路径**：安全、隐私、外部写操作、部署、资金、账号或工业设备。执行完整流程，并增加 Dry Run、回滚、单次 Canary 和真实环境验证。

以下五个门禁适用于标准路径和高风险路径：

1. 没有复用决策，不开始自建。
2. 没有设计批准，不写代码。
3. 最小纵向闭环未通过，不扩大并行。
4. 没有逐项验收对账和证据，不声明完成。
5. 没有安全和发布检查，不对外发布。

## 执行流程

为非快速路径创建或更新任务计划，并按以下顺序推进。

### 1. GitHub 复用优先

在第一个正式开发步骤中，只先收集搜索所需的一句话目标、必需功能、平台和不可妥协约束。

完整读取 [GitHub 复用门禁](references/github-reuse-gate.md)，搜索并验证相似项目。输出“直接使用、使用并扩展、只借鉴、自建”之一，证据等级只使用 E1、E2 或 E3，不另造分级。

**硬门禁：复用调研阶段唯一合法的回合结束状态是用户可见的“复用决策”。** 在结束回合、暂停或请求确认前，必须输出候选、证据等级、明确推荐、理由、搜索限制和下一步。不要以“继续搜索”“稍后收敛”“准备输出”等内部进度句结束。

发现高度匹配项目时，明确建议直接使用并暂停自建。用户同意后先安全试运行，不立即接入真实凭据或生产数据。

GitHub 无法访问时，说明搜索不完整。未经用户确认，不跨过复用门禁开始自建。

当用户新增或改变平台、部署方式、必需功能、数据边界、许可证或维护约束，且变化可能影响候选适用性时，重新评估复用决策。说明原结论、变化原因和新结论；不机械重复全部搜索，只补查受影响的候选与证据。

### 2. 现状与代码考古

只在决定扩展或自建后执行：

1. 检查项目文档、测试、工作区修改和近期提交，保留用户已有修改。
2. 如果仓库根目录存在 `.codegraph/`，理解和定位代码时先使用 CodeGraph，再考虑 `rg`、文件遍历和逐文件读取。
3. 如果不存在 `.codegraph/`，主动建议执行 `codegraph init`，说明它会创建索引、写入项目目录并可能需要时间。
4. 等待用户明确确认后才初始化；不得自动执行。
5. 用户拒绝、工具不可用或初始化失败时，降级使用文档、Git、测试和 `rg`，不要阻塞任务。
6. 输出简短现状快照：入口、数据流、关键依赖、既有规范、风险边界和工作区状态。

### 3. 澄清并批准设计

优先调用 `brainstorming` 或可用的 Trellis brainstorming 能力。每次只问一个阻断性问题，同时给出推荐、理由和代价。

只把真正改变范围、架构、成本、安全或数据边界的问题交给用户逐项决定。对非阻断性选择给出推荐默认值并集中写入设计，避免把一个设计拆成连续的低价值审批。

明确目标、非目标、验收标准、模块边界和失败行为。小任务在聊天中确认；复杂任务才持久化规格。用户批准设计前不要实现。

### 4. 先设计证据路径

优先调用 `verification-planning`。完整读取 [验证与发布](references/verification-and-release.md)，根据任务风险确定静态检查、自动测试、运行验证、真实环境验证和人工验收。

明确区分 Mock、自动测试、构建成功和真实环境验证。凭据只来自环境变量或安全存储；不要把密钥写入代码、提示、日志或仓库。

### 5. 完成最小纵向闭环

先实现一条贯穿真实系统的最小路径，例如：

`启动程序 → 用户操作 → 后端处理 → 数据保存 → UI 返回结果`

用真实契约验证这条路径。孤立组件或 Mock 成功不能替代纵向闭环。

### 6. 受控实现与并行

优先调用可用的 Trellis implementation 能力，否则按批准计划实施。

- 默认串行完成核心契约和集成路径。
- 只并行相互独立的工作，通常最多 2–3 条工作线。
- 为每条工作线给出明确输入、输出、文件范围和验证命令。
- 每批工作后立即集成，不把全部合并推迟到最后。
- 主代理持续负责接口一致性、集成和验收。
- 行为正确后再调用 `simplify` 做聚焦的维护性优化。

跨多个子系统、预计跨会话或验收项较多的长任务，先拆成可独立验收的里程碑。每个里程碑都要有范围、退出条件和证据；一次只保持一个核心里程碑处于进行中。只在完成、阻塞或下一步发生实质变化时汇报状态，不用“继续”“处理中”“仍在推进”等无新信息的句子占用回合。

原则：并行调研，串行确定契约和系统集成。

### 7. 集成、排错与验收

先验证主流程，再验证边界和失败路径。优先调用可用的 Trellis check 能力。

同一实现、验证、写入、工具或权限路径连续两次失败后停止重复尝试。先判断问题属于代码、环境、权限还是工具状态，再调用 `break-loop`、选择不同证据路径或明确报告阻塞；不要只更换措辞重复请求，也不要把升级权限当作默认重试。

重要的本地写入完成后，必须用重新读取、`rg`、`git diff`、文件哈希或运行结果中的至少一种方式核验实际落盘。工具返回“成功”不单独构成写入证据。

验收结论必须附命令、输出、截图、构建产物或真实运行证据。完成前把每一项已批准的验收标准映射为“已验证、部分验证、未验证或不适用”，并记录对应证据或缺口。仍有必需项未验证时，只能报告部分完成；不要用总体构建成功掩盖单项缺口。

### 8. 发布、交接与沉淀

按 [验证与发布](references/verification-and-release.md) 执行安全和发布检查。目标平台为 Windows 时，优先提供一键启动和普通用户能理解的错误提示。

报告逐项验收对账、已验证与未验证范围、产物、已知限制和回滚方式。只有形成重复模式或重要教训时才调用 `reflect` 或等价的经验沉淀能力。

## 处理不确定性与降级

- GitHub 不可用：披露搜索不完整，等待是否继续自建的决定。
- CodeGraph 被拒绝或失败：降级到文档、Git、测试和 `rg`。
- 真实环境不可用：标记未验证，给出可执行的人工验证步骤。
- 本地写入结果不确定：重新读取或检查差异，确认实际落盘后再继续。
- 外部写结果不确定：禁止重试，先核验外部状态。
- 工具或权限路径连续失败：停止同路径重试，分类根因并报告替代路径或阻塞。
- 某项 Skill 不可用：执行能力等价的简化流程，不中断任务。
- 需要删除、覆盖、发布、部署或改变外部状态：先确认具体目标和影响。
- 除非用户明确要求，不提交、不推送、不创建 PR、不发布也不部署。

不要为满足流程制造无价值文档。快速任务默认在聊天中输出；标准和高风险任务遵循项目已有文档约定。没有约定时先说明推荐位置。
