# 验证与发布

## 目录

- 1. 按风险选择证据深度
- 2. 先证明最小纵向闭环
- 3. 项目类型重点
- 4. 凭据与敏感数据
- 5. 核验实际写入
- 6. 排错规则
- 7. 逐项验收对账
- 8. 发布前检查与完成报告

在实现前建立从“需要成立的主张”到“可以支持或否定它的证据”的路径。验证成本与风险相称，但任何路径都不能把弱证据包装成强结论。

## 1. 按风险选择证据深度

### 快速路径

- 检查改动范围和工作区安全。
- 运行最接近改动的原生检查。
- 确认没有改变未请求的行为。

### 标准路径

- 静态检查：格式、类型、依赖和安全扫描。
- 自动测试：单元、集成和回归。
- 运行验证：真实启动和关键用户路径。
- 环境验证：目标操作系统、浏览器、设备或网络条件。
- 记录未覆盖的边界。

### 高风险路径

在标准路径上增加：

- Dry Run 或只读预览。
- 明确审批点与不可逆影响。
- 单次最小 Canary。
- 可执行回滚或恢复方案。
- 不确定外部写入的状态核验，禁止盲目重试。
- 失败注入或关键异常路径验证。

## 2. 先证明最小纵向闭环

定义一条贯穿真实边界的最小路径。记录：

- 起始状态和可控输入。
- 跨越的 UI、API、进程、数据库、文件或设备边界。
- 可观察结果和持久化状态。
- 失败时可用于定位的日志或诊断信息。
- 重复或恢复场景的方法。

闭环未通过前不要扩大并行。Mock 可用于局部开发，但不能证明真实契约已经集成。

## 3. 项目类型重点

| 类型 | 必查证据 |
| --- | --- |
| Windows 本地程序 | 全新终端启动、一键启动、路径与编码、缺失依赖、可理解错误、打包产物 |
| Web 应用 | 前后端真实联通、刷新与持久化、错误状态、构建、浏览器关键路径 |
| 移动应用 | 目标设备或模拟器启动、权限、离线/恢复、打包产物、平台差异 |
| 外部只读 API | 真实响应模式、超时、限流、缓存、错误映射、凭据缺失 |
| 外部写操作 | Dry Run、幂等或状态查询、单次 Canary、禁止不确定重试、审计和回滚 |
| 隐私或安全 | 威胁边界、认证授权、输入验证、日志脱敏、密钥管理、默认绑定范围 |
| 工业设备或生产数据 | 真实设备/数据复现、离线与断连、时序、恢复、长期运行和人工回退 |

## 4. 凭据与敏感数据

- 从环境变量或系统安全存储读取凭据。
- 不在代码、配置示例、提示、日志、截图和提交中暴露密钥。
- 发现疑似已泄露凭据时停止继续传播，建议立即轮换并清理历史。
- 测试默认使用非生产账号、最小权限和可恢复数据。

## 5. 核验实际写入

重要修改不能只依赖编辑工具的返回值。根据项目选择至少一种直接证据：

- 重新读取目标位置，确认预期内容与类型已经落盘。
- 用 `rg`、`git diff` 或文件哈希确认修改范围。
- 运行能覆盖该修改的最小检查，观察行为或产物变化。

发现工具报告成功但磁盘内容未变化时，把本次写入视为失败，不继续基于假定状态实施后续步骤。

## 6. 排错规则

- 先复现并保存原始错误、输入、环境和状态。
- 同一实现、验证、写入、工具或权限路径连续失败两次后停止重复尝试。
- 先区分代码、环境、权限和工具故障，再选择不同证据路径或报告阻塞。
- 优先增加最小的可观察性，而不是堆叠补丁。
- 外部写结果不确定时先查询实际状态，不自动重试。
- 无法验证时明确写“未验证”，提供人工步骤。

## 7. 逐项验收对账

完成前逐项核对所有已批准的验收标准：

| 验收项 | 状态 | 证据 | 缺口/下一步 |
| --- | --- | --- | --- |
| 具体标准 | 已验证 / 部分验证 / 未验证 / 不适用 | 命令、输出、截图、产物或运行路径 | 未覆盖边界、阻塞原因或后续动作 |

不能用“总体测试通过”替代单项对账。只要仍有必需项处于部分验证或未验证，整体结论就是部分完成，除非用户明确批准缩小范围或接受该限制。

## 8. 发布前检查与完成报告

- 工作区不包含凭据、缓存、临时文件、测试数据或调试配置。
- 项目原生检查和构建通过。
- 构建产物在目标环境可启动。
- 最小纵向闭环和关键失败路径有证据。
- 数据迁移、兼容性、回滚和恢复方式明确。
- 用户可见文档、错误信息和启动方式与实际一致。
- 所有重要写入已经核验实际落盘。
- 已验证、部分验证和未验证范围已经区分。

使用以下结构，省略不适用项但不要省略验证边界：

```markdown
## 完成结果

- 实现：
- 主要取舍：

## 验收对账

| 验收项 | 状态 | 证据 | 缺口/下一步 |
| --- | --- | --- | --- |

## 验证证据

- 已验证：命令、结果、产物或真实运行路径
- 部分验证：已证明部分与剩余限制
- 未验证：原因和人工验证步骤

## 发布与风险

- 产物/启动方式：
- 已知限制：
- 回滚或恢复：
```

只有证据支持目标主张时才声明完成。构建成功不等于程序真实可用，Mock 成功不等于外部系统已经验证。
